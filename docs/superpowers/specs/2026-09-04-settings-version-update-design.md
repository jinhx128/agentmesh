# 关于页版本与更新模块收敛设计

## 背景

关于页当前分别展示“版本信息”和“版本更新”两张卡片。两张卡片都展示当前版本，造成重复；运行时版本、当前入口和最低写入版本属于排障元数据，不适合占据日常主界面。

## 目标

- 将“版本信息”和“版本更新”合并为一个“版本与更新”模块。
- 默认只展示用户需要判断更新状态的信息。
- 兼容性异常时保留清晰、可操作的升级提示。
- 保持现有更新检查接口、兼容性判断、CLI/桌面端更新行为不变。
- 保持“应用更新”模块独立，因为它负责桌面端下载、安装、重启和自动检测偏好。

## 方案

`SettingsAboutPanel` 保留现有关于页外层容器。将 `studio-compatibility-card` 和 `settings-update` 两个子卡片替换为一个 `settings-version-update` 卡片：

- 卡片标题为“版本与更新”。
- 右侧保留“重新检查”按钮、更新状态文字和状态徽标。
- 正常状态下只保留四个信息项：当前版本、最新版本、CLI 更新、桌面端更新。
- 保留 CLI 更新命令和桌面端下载信息，但仅在服务端返回对应资产时展示。
- 不再展示运行时版本、当前入口、最低写入版本和最后更新时间。
- 兼容性为 `read_write` 时不显示兼容性徽标和技术说明；为 `read_only` 或 `refused` 时，在同一模块内显示一条升级提示，并保留已有诊断原因列表。
- loading、error 和缺少更新报告时继续提供现有可理解的状态反馈。
- “应用更新”卡片及自动检测开关保持现状和独立布局。

只调整 Studio 前端呈现，不删除后端返回字段，也不改变本地兼容性元数据和更新报告的数据契约。

## 数据流与错误处理

现有 `SettingsAboutState`、`StudioCompatibilityDiagnostics` 和 `StudioUpdateReport` 继续作为数据来源。新的卡片只负责组合展示：

1. 兼容性状态用于决定是否显示异常提示。
2. 更新报告用于填充版本和 CLI/桌面端状态。
3. 更新检查失败仍在卡片内显示错误和“重新检查”。
4. 兼容性读取失败仍沿用页面级错误状态，避免显示看似可信的版本判断。

## 测试

- 更新 Studio UI 定向断言：验证只存在一个版本与更新模块，四个默认信息项顺序稳定。
- 验证正常兼容性不渲染运行时版本、入口、最低写入版本和最后更新时间。
- 验证只读/拒绝兼容性仍渲染升级提示和诊断原因。
- 验证更新 loading、error、current 和 update-available 状态。
- 运行 `npm test`、前端构建和 `git diff --check`。

## 非目标

- 不修改更新检查 API 或桌面端 updater。
- 不删除兼容性字段和后端数据。
- 不合并下方的“应用更新”卡片。
- 不迁移或兼容历史数据。
